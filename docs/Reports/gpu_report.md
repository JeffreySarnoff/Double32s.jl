| operation | registers | local (B) | shared (B) | max threads | occupancy |
|:----------|----------:|----------:|-----------:|------------:|----------:|
| `+` | 18 | 32 | 0 | 768 | 1.00 |
| `*` | 31 | 56 | 0 | 768 | 1.00 |
| `/` | 33 | 88 | 0 | 768 | 1.00 |
| `fma` | 45 | 80 | 0 | 640 | 0.83 |
| `sqrt_or_nan` | 26 | 32 | 0 | 768 | 1.00 |
| `reduce_stage` | 10 | 0 | 2048 | 768 | 1.00 |

`local` is spill space. The Phase 3 gate is "no spills or
occupancy collapse": occupancy stays at or near 1.0 for every
operation except `fma`, whose 45 registers cost some occupancy and
buy a fused three-operand kernel. `test/kernels.jl` asserts a floor
on occupancy and a ceiling on spill space, so a future change that
regresses either one fails rather than being noticed here later.

`AcceleratedKernels.mapreduce`; `block_size` is its knob.

## Tiled matrix multiply (design 19.5)

Both element types. `Float32` operands get **exact** products via
`two_prod_`; `Double32` operands use the ordinary pair multiply.
Errors are normwise: `max|C - Cref| / max|Cref|`.
The split-channel inner op holds the kernel within ~7-9x of cuBLAS
SGEMM at 1024³ — for about seven more decimal digits. No vendor
library accumulates `Double32`, so nothing faster exists at this
accuracy.

| size | F32→D32 | D32×D32 | `Float32` `*` | D32 rel err | F32 rel err |
|-----:|--------:|--------:|--------------:|------------:|------------:|
| 256³ | 0.02 ms | 0.02 ms | 0.015 ms | 8.66e-14 | 8.69e-07 |
| 512³ | 0.05 ms | 0.07 ms | 0.017 ms | 1.29e-13 | 7.28e-07 |
| 1024³ | 0.36 ms | 0.43 ms | 0.053 ms | 1.68e-13 | 5.99e-07 |

The accuracy column is the reason to use it: `Float32` data
multiplied in `Float32` loses about seven digits, the same data
multiplied with exact products and `Double32` accumulation loses
about one. Results are bit-identical between the CPU and CUDA
backends for a fixed tile size.

## Why there is no direct CUDA reduction kernel

Design section 15.5 permits a direct `CUDA.@cuda` kernel only when it
is *materially faster* than the KernelAbstractions baseline. Three
candidates were implemented and measured; none qualified.

| candidate | result |
|:----------|:-------|
| full warp-shuffle reduction (§15.2) | **0.48–0.56×** — i.e. about half the speed |
| hybrid: shared-memory tree to 32 lanes, then shuffle | 0.99–1.10×, inside noise |
| direct CUDA kernel, same tree as KA | 1.5% after the fix below |

The warp-shuffle result inverts the usual advice, for a reason worth
recording: a shuffle round makes **every** lane perform the operator,
while a tree round halves the live lanes. With a 1-flop `Float32`
operator that trade is worth it to remove barriers; with a 20-flop
`Double32` addition it is not. Tested on a cheap operator
(`Float32` `max`) the hybrid reaches only 1.07× at the default
workgroup size — still not material.

The direct kernel's apparent 8% edge turned out to be an artifact:
the KA driver was calling `synchronize` after *every* reduction pass.
Successive launches on one backend are queue-ordered, so those syncs
were unnecessary. Removing them took `sum(Double32, A)` from 0.444 ms to
0.414 ms and closed the gap to 1.5%. The fix is portable — every
backend gets it — which is strictly better than a vendor-specific
duplicate of the same algorithm.
